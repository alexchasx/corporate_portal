## 1. Резюме и цели

Корпоративный веб-портал — единая точка доступа сотрудников (10 000+ активных пользователей) к корпоративным сервисам, документам, коммуникациям и бизнес-процессам. Пиковая нагрузка — до 3 000 одновременных сессий. Развёртывание on-premise / приватное облако, горизонтальное масштабирование, доступ из LAN и через VPN/mTLS.

**Цели документа:**

- Зафиксировать целевую архитектуру и ключевые технические решения.
- Определить структуру репозиториев, стандарты кода и процессы разработки.
- Разбить работу на этапы с вехами, результатами и критериями выхода.
- Согласовать подходы к тестированию, безопасности, CI/CD, мониторингу и эксплуатации.

**Ключевые показатели успеха (из раздела 5 НФТ):**

| Метрика | Цель |
|---|---|
| Время ответа API (P95) | ≤ 300 мс при штатной нагрузке; ≤ 500 мс при 3 000 пользователей |
| Первая отрисовка (FCP) | ≤ 1,5 с |
| Lighthouse Performance | ≥ 85 |
| Lighthouse Accessibility | ≥ 90 |
| Доступность | 99,5 % |
| Покрытие тестами backend | ≥ 70 % (unit + feature) |

## 2. Технологический стек и обоснование

### 2.1. Стек (по требованиям + дополнения)

| Слой | Технология | Версия | Назначение |
|---|---|---|---|
| Backend | Laravel | 13 | API, бизнес-логика, очереди, события |
| Runtime | PHP | 8.4+ | — |
| БД | PostgreSQL | 18+ | Основное хранилище, FTS, партиционирование |
| Frontend | Nuxt.js | 4+ | SSR/SPA-гибрид (Nitro) |
| UI | Vue 3 + Vuetify | 3 | Компонентная библиотека |
| Кэш / очереди / сессии | Redis | 7+ | Кэш, очереди, сессии, pub/sub |
| WebSocket | Laravel Reverb (или Soketi) | — | Уведомления, чат |
| Файлы | MinIO (S3-совместимое) | — | Медиа, вложения, документы |
| Поиск | PostgreSQL FTS + pg_trgm (MVP) → OpenSearch (опционально) | — | Глобальный поиск |
| Веб-сервер | Nginx | — | TLS, HTTP-кэш, rate limiting, балансировка |
| Контейнеризация | Docker, Docker Compose | `php:8.4-fpm-trixie-slim` | Backend-образ |
| CI/CD | GitLab CI / GitHub Actions | — | Пайплайны |
| Мониторинг | Prometheus + Grafana + Sentry | — | Метрики, алерты, ошибки |
| E2E / Нагрузка | Playwright / k6 | — | E2E-пути, нагрузочное тестирование |

### 2.2. Обоснование ключевых решений

- **Модульный монолит, а не микросервисы.** Одна БД, транзакционная целостность на уровне приложения, простая эксплуатация и отладка. Модули строго изолированы по Bounded Context (HR, Документооборот, Новости, Опросы, Справочники, Задачи). При росте нагрузки проблемный модуль выделяется в сервис без переписывания остальных (изоляция через контракты).
- **Nuxt SSR/SPA-гибрид per-route.** Контентные страницы (новости, документы, справочники) — SSR ради SEO/FCP и доступности; интерактивные модули (канбан, конструктор опросов, личный кабинет) — SPA ради UX. Управляется через `routeRules` Nitro.
- **PostgreSQL FTS как стартовый поиск.** Меньше компонентов для эксплуатации, транзакционная согласованность с данными. `pg_trgm` — для поиска по ФИО. Интерфейс поиска абстрагируется (SearchService), чтобы позже заменить на OpenSearch без переписывания бизнес-кода.
- **Reverb как основной WebSocket-сервер.** Нативный для Laravel, деплоится как PHP-воркер, не добавляет Node-инфраструктуру. Soketi — резервный вариант.
- **MinIO вместо «голого» диска.** Единый S3-интерфейс (Laravel Filesystem), прозрачный переход на облачный S3, версионирование объектов из коробки.

## 3. Целевая архитектура

```
                      +-------------------------------------+
                      |             Клиенты                 |
                      |  Browser (LAN/VPN) / Mobile (VPN)   |
                      +----------------+--------------------+
                                       | HTTPS (TLS 1.3, HSTS, mTLS для VPN)
                          +------------v----------------+
                          |          Nginx / LB         |
                          |  TLS termination, HTTP-кэш,  |
                          |  rate limiting, WAF-правила  |
                          +-----+------------------+----+
                                |                  |
                +---------------v--+        +------v------------------+
                |  Nuxt 4 (Nitro)  |        |  Laravel 13 (API)      |
                |  SSR + SPA       |        |  модульный монолит,    |
                |  per-route rules |        |  домены: Auth, HR, News,|
                |  Vue 3, Vuetify  |        |  Docs, Tasks, Surveys, |
                +--------+---------+        |  Directory, Search,    |
                         |                  |  Admin                 |
                         |  REST/JSON       +---+----+----+----+-----+
                         |  (OpenAPI)           |    |    |    |
                         +----------------------+    |    |    |
                                    +----------------+    |    |
                                    |    +----------------+    |
                                    v    v                     v
                 +------------------+----+------+-----------------------+
                 |  PostgreSQL 18   | Redis 7   |  MinIO (S3)          |
                 |  primary +       | кэш,      |  файлы, медиа,       |
                 |  read-replicas   | очереди,  |  документы           |
                 |  (партициониро-  | сессии,   |                      |
                 |   вание)         | pub/sub   |                      |
                 +------------------+-----------+----------------------+
                                   |
                        +----------v-----------+
                        |  Reverb (WebSocket)   |
                        |  уведомления, чат     |
                        +----------+-----------+
                                   |
                       +-----------+------------+------------+
                       | LDAP/AD  | СЭД REST/SOAP| ERP (1C/SAP)|
                       | SMTP/IMAP| FCM/APNs     | Prometheus  |
                       +----------+--------------+-------------+
```

**Потоки запросов:**

1. **Контентная страница** (например, новости): браузер → Nginx → Nuxt (SSR) → API Laravel → PostgreSQL/Redis. Готовый HTML отдаётся с HTTP-кэшем Nginx.
2. **Интерактивный модуль** (канбан): браузер → Nginx → Nuxt (SPA) → API → Laravel → БД/Redis; обновления — через Reverb WebSocket.
3. **Тяжёлые операции** (рассылка, импорт оргструктуры, отчёт): API кладёт Job в очередь Redis → воркер обрабатывает → статус/уведомление пользователю через WebSocket.
4. **Интеграции**: адаптеры в модулях (`Contracts` + реализации) — LDAP-синхронизация по расписанию, СЭД по REST/SOAP, ERP по REST/OData, почта через SMTP, push через FCM/APNs.

## 5. Backend: модульный монолит Laravel 13

### 5.1. Структура модулей

```
backend/app/Modules/
├── Auth/                  # LDAP, SSO, 2FA, сессии, токены
│   ├── Http/Controllers/, Requests/
│   ├── Services/          # бизнес-логика
│   ├── Actions/           # одиночные сценарии (LoginAction и т.п.)
│   ├── Models/            # локальные модели пользователя, сессий
│   ├── Policies/          # RBAC/ABAC-проверки
│   ├── Events/ Listeners/ Jobs/
│   ├── Contracts/         # интерфейсы для межмодульного обмена
│   ├── Database/Migrations/
│   └── routes/api.php     # маршруты модуля
├── HR/                    # профили, оргструктура, должности
├── News/                  # ленты, комментарии, модерация
├── Documents/             # библиотека, версии, подписи, ЖЦ
├── Tasks/                 # задачи, канбан, дедлайны
├── Surveys/               # конструктор, голосования, результаты
├── Directory/             # справочники, телефонный справочник
├── Search/                # абстракция над FTS/OpenSearch
└── Admin/                 # пользователи, роли, аудит, конфигурация
```

### 5.2. Паттерны и практики

- **Services + Actions**: контроллеры тонкие; сценарии — отдельные Action-классы (один класс = один юз-кейс), переиспользуемые из контроллеров и Job-ов.
- **Form Requests** для валидации; валидация на границе каждого модуля.
- **Авторизация** — Laravel Policies (RBAC) + кастомный ABAC-сервис для контекстных правил (подразделение, иерархия руководителей, статус сотрудника, чувствительность документа).
- **События + очереди**: межмодульная связь только через Events/Contracts (без прямых зависимостей модулей друг от друга). Тяжёлая работа — в Jobs с Redis-драйвером очередей, ретраи, дед-леттер.
- **DTO** для данных между модулями; типизация PHP 8.4 (properties, enums, readonly).
- **Eloquent**: query scopes, eager loading, индексы через миграции; N+1 контролируется на code review и через debug-профилировщик.
- **Миграции** — только через Laravel migrations; для destructive-изменений обязательна reverse-миграция; прод-применение через пайплайн с бэкапом.
- **События модели** → аудит-лог (audit_logs), уведомления (notifications).

### 5.3. Аутентификация и авторизация

```
+-----------+    1. login/password      +------------------+
|  Клиент   | ------------------------> |  AuthController  |
+-----------+                           +--------+---------+
                                                |
                                                v
                              +-----------------+-----------------+
                              | LDAP (ldaprecord-laravel)         |
                              | проверка учётных данных против AD |
                              +-----------------+-----------------+
                                                |
                              успех (или fallback на локального)
                                                |
                              +-----------------v-----------------+
                              | Upsert локального пользователя    |
                              | (синхронизация атрибутов из AD)   |
                              +-----------------+-----------------+
                                                |
                              +-----------------v-----------------+
                              | 2FA: TOTP, если включено          |
                              | (spatie/laravel-google2fa)        |
                              +-----------------+-----------------+
                                                |
                              +-----------------v-----------------+
                              | Выдача: session (Redis) для web,  |
                              | Sanctum-токен для API/mobile      |
                              +-----------------+-----------------+
```

- **SSO**: SAML 2.0 / OAuth 2.0 (Socialite или корпоративный IdP) — подключается параллельно с LDAP-паролем как альтернативный источник входа.
- **Сессии**: Redis-драйвер; таблица `sessions` для списка активных сессий и принудительного logout.
- **RBAC**: роли/права (spatie/permission или собственная реализация).
- **ABAC**: атрибуты пользователя (подразделение, уровень доступа, руководитель) + контекст ресурса (видимость документа, квота опроса).

### 5.4. Кэширование и очереди

- **Redis-кэш**: справочники, оргструктура, права пользователя (инвалидация через cache tags + события модели).
- **HTTP-кэш**: Nginx для публичных страниц новостей; заголовки `Cache-Control` с ETag.
- **Очереди**: отдельные connection/queue по назначению: `notifications`, `imports`, `reports`, `default`. Воркеры с автоскейлингом по глубине очереди (k8s HPA / supervisor + скрипты).
- **Публикация по расписанию**: scheduler Laravel (крон-контейнер) для новостей, LDAP-синхронизации, напоминаний о дедлайнах, очистки устаревших сессий.

### 5.5. Ключевые пакеты

| Пакет | Назначение |
|---|---|
| `ldaprecord/laravel` | LDAP/AD-аутентификация и синхронизация |
| `laravel/sanctum` | API-токены, stateless-аутентификация |
| `spatie/laravel-permission` | RBAC |
| `spatie/laravel-translatable` | Мультиязычность моделей |
| `spatie/laravel-activitylog` или своя реализация | Аудит-журнал |
| `laravel/scramble` (или `dedoc/scramble`) / `knuckleswtf/scribe` | OpenAPI из кода |
| `spatie/laravel-health` или свои роуты | Health-check (БД, Redis, S3, LDAP) |
| `laravel/prometheus` (spatie) + Sentry SDK | Метрики и ошибки |
| `laravel/reverb` | WebSocket-сервер |
| `phpstan/phpstan` (level 8), `friendsofphp/php-cs-fixer` | Статический анализ и стиль |

## 6. Frontend: Nuxt 4 + Vue 3 + Vuetify 3

### 6.1. Структура

```
frontend/
├── app/
│   ├── pages/           # маршруты (роутинг Nuxt)
│   ├── layouts/         # default, auth, admin
│   ├── components/      # Vuetify-компоненты (BaseButton и т.п.)
│   ├── composables/     # useApi, useNotification, usePermissions
│   ├── stores/          # Pinia: session, permissions, ui
│   ├── middleware/      # auth.ts, roles.ts
│   ├── plugins/         # vuetify, i18n, api-client
│   ├── utils/api.ts     # единый fetch-клиент (Auth-заголовки, retry)
│   └── types/           # TS-типы, сгенерированные из OpenAPI
├── nuxt.config.ts
├── vitest.config.ts
└── e2e/                 # Playwright
```

### 6.2. SSR/SPA per-route

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  routeRules: {
    '/news/**':        { ssr: true },   // контент — SSR + статический кэш
    '/documents/**':   { ssr: true },
    '/directory/**':   { ssr: true },
    '/dashboard/**':   { ssr: false },  // интерактивные — SPA
    '/tasks/**':       { ssr: false },
    '/surveys/**':     { ssr: false },
    '/admin/**':       { ssr: false },
  },
  // nitro, modules: vuetify, i18n, pinia
})
```

### 6.3. Состояние и данные

- **Pinia**: глобальное состояние (текущий пользователь, права, уведомления, UI).
- **Данные**: `useFetch`/`useAsyncData` с ключами и `staleTime` (SWR-подход), payload-кэш Nitro на SSR; избегать дублирования запросов на клиенте/сервере.
- **Real-time**: подключение к Reverb (echo-клиент), обновление уведомлений и канбана через WebSocket.
- **Ошибки**: единый интерцептор (toast, редирект на 401, graceful degradation при недоступности API-модулей).

### 6.4. Локализация

- `@nuxtjs/i18n` (vue-i18n): ru + en из коробки, lazy-load переводов, локализация дат/чисел (Intl).
- Ключи переводов централизованы; backend-контент локализуется через Laravel Translatable (`ru`/`en` поля JSON).

### 6.5. Адаптивность и доступность

- Mobile-first; брейкпоинты Vuetify 3 без переопределения базовой сетки; 360px — 4K.
- WCAG 2.1 AA: семантическая разметка, aria-атрибуты, контраст, полная навигация с клавиатуры, фокус-трапы для модалок.
- Кроссбраузерность: Chrome, Firefox, Safari, Edge; iOS 15+, Android 10+ (проверка в Playwright-матрице).

## 7. Модель данных PostgreSQL 18

### 7.1. Основные сущности

| Модуль | Таблицы |
|---|---|
| Auth/HR | `users`, `user_profiles`, `departments` (adjacency list), `department_tree` (materialized path/closure), `positions`, `roles`, `permissions`, `role_permissions`, `model_has_roles` |
| News | `news`, `news_tags`, `news_tag_news`, `news_comments`, `news_media`, `news_pins` |
| Documents | `document_categories`, `documents`, `document_versions`, `document_workflow_states`, `document_signatures` |
| Tasks | `tasks`, `task_statuses`, `task_assignees`, `task_comments`, `task_attachments` |
| Surveys | `surveys`, `survey_questions`, `survey_options`, `survey_responses`, `survey_response_answers` (анонимные ответы — без FK на `users`) |
| Directory | `directory_entries`, `phone_book`, `regulations` |
| System | `sessions`, `audit_logs`, `notifications`, `notification_subscriptions`, `config_settings`, `search_index` (опционально) |

### 7.2. Упрощённая ERD

```
+-------------+       +--------------+       +---------------+
| departments |<------| users        |------>| positions     |
| id,parent_id|  N:1  | id,dept_id, |  N:1  | id,title      |
+------+------+       | position_id,|       +---------------+
       |              | ldap_dn,... |
       |              +------+------+
       |                     | 1:N
       |        +------------+--------------+
       |        v               v           v
       |  +----------+   +----------+  +----------+
       |  | news     |   | tasks    |  | documents|
       |  +----------+   +----------+  +----------+
       |  | surveys  |   | survey_* |  | audit_logs|  (партиц.)
       +--------------->+ directory_entries, phone_book
```

### 7.3. Партиционирование и индексы

- **Партиционирование по диапазону дат** для растущих таблиц: `audit_logs`, `notifications` (по месяцам), `news_comments` при росте.
- **Индексы**: GIN для полнотекстового поиска (`to_tsvector('russian', ...)`), `pg_trgm` (GIN/gin_trgm_ops) для поиска по ФИО и частичным совпадениям, составные индексы под типовые фильтры (dept_id + status), partial indexes для активных сущностей.
- **Read-replica**: чтение тяжёлых отчётов и поиска — на реплику; запись — на primary.
- **Резервирование**: ежедневный инкрементальный + еженедельный полный бэкап (pgBackRest/WAL-G), хранение 30 дней, регулярные тесты восстановления.

### 7.4. Поиск

- MVP: `SearchService` с PostgreSQL FTS (новости, документы) + ILIKE/pg_trgm (люди, справочники). Фасеты — отдельные SQL-агрегации.
- Опционально: синхронизация в OpenSearch (Jobs после записи) для масштаба/точности. Интерфейс `Contracts\SearchProvider` позволяет менять провайдер.

## 8. API-дизайн

### 8.1. Конвенции

- Базовый путь: `/api/v1`; версионирование через префикс, обратная совместимость минимум 1 мажорная версия.
- RESTful: коллекции/сущности, глаголы через HTTP-методы.
- Ответы: `{ "data": ... }` / `{ "data": [...], "meta": { "pagination": {...} } }`.
- Ошибки: `{ "error": { "code": "...", "message": "...", "details": [...] } }`, соответствие HTTP-статусам.
- Пагинация: cursor-based для лент (новости, уведомления), page-based для таблиц админки.
- Фильтрация/сортировка: query-параметры `filter[dept_id]=`, `sort=-created_at`.
- Rate limiting: `throttle` на аутентификацию (по IP), на API — по токену/пользователю.

### 8.2. Основные группы эндпоинтов

| Модуль | Примеры |
|---|---|
| Auth | `POST /auth/login`, `POST /auth/2fa/verify`, `POST /auth/logout`, `GET /auth/sessions`, `DELETE /auth/sessions/{id}` |
| Users/HR | `GET /users`, `GET /users/{id}`, `PATCH /me`, `GET /departments/tree`, `POST /org/import` |
| News | `GET /news`, `GET /news/{id}`, `POST /news`, `POST /news/{id}/comments`, `POST /news/{id}/pin` |
| Documents | `GET /documents`, `GET /documents/{id}/versions`, `POST /documents/{id}/approve`, `POST /documents/{id}/sign` |
| Tasks | `GET /tasks`, `POST /tasks`, `PATCH /tasks/{id}`, `GET /tasks/kanban`, `GET /tasks/gantt` |
| Surveys | `GET /surveys`, `POST /surveys`, `POST /surveys/{id}/responses`, `GET /surveys/{id}/results` |
| Directory | `GET /directory/phone-book`, `GET /regulations` |
| Search | `GET /search?q=&types=news,users` |
| Notifications | `GET /notifications`, `PATCH /notifications/{id}/read`, `GET /notifications/subscriptions` |
| Admin | `GET/POST/PATCH /admin/users`, `/admin/roles`, `/admin/config`, `GET /admin/audit`, `GET /admin/metrics` |

### 8.3. OpenAPI

- Генерация из кода (Scramble или Scribe) — спецификация выкладывается в `docs/`, используется для авто-генерации TS-типов фронтенда (`openapi-typescript`).

## 9. Инфраструктура и развёртывание (Docker)

### 9.1. Dev/Staging: docker-compose

| Сервис | Образ/роль |
|---|---|
| `nginx` | фронт-прокси, TLS (dev — self-signed), HTTP-кэш |
| `backend` | `php:8.4-fpm-trixie-slim` + composer-зависимости |
| `worker` | тот же образ, `php artisan queue:work` |
| `scheduler` | тот же образ, `php artisan schedule:work` |
| `reverb` | тот же образ, WebSocket-сервер |
| `frontend` | Node-образ для сборки + Nitro-сервер (или статика за Nginx) |
| `postgres` | `postgres:18` (+ реплика в staging) |
| `redis` | `redis:7` |
| `minio` | S3-хранилище для dev/staging |
| `mailpit` | перехват почты в dev |

Критерий приёмки: развёртывание из одного `docker compose up` (раздел 9 требований).

### 9.2. Production-топология

- Nginx/HAProxy LB перед группой stateless-инстансов backend и frontend (горизонтальное масштабирование).
- PostgreSQL: primary + read-replicas; Redis: sentinel/кластер.
- Деплой через `deploy/` (Helm для k8s или Ansible для bare-metal) — решение фиксируется на этапе 0.
- **Graceful degradation**: фронтенд продолжает работать при недоступности поиска/уведомлений (fallback-UI, флаги фич).

### 9.3. Секреты

- Vault (предпочтительно) или env-переменные контейнера; **никогда** не в репозитории. `.env.example` — только плейсхолдеры.
- Ротация сертификатов и ключей через CI/CD-скрипты.

### 9.4. Миграции и релизы

- Миграции — отдельный шаг пайплайна перед выкаткой кода (expand/contract: сначала аддитивные, потом destructive с reverse-миграцией).
- Zero-downtime: деплой с перезапуском по одному инстансу, health-check перед включением в ротацию.

## 10. Безопасность

- **Транспорт**: TLS 1.3, HSTS, CSP-заголовки; mTLS для внешнего доступа.
- **OWASP Top 10**: CSRF-токены (web), XSS-санитизация (DOMPurify для rich-text, `purify` на бэкенде), parameterized queries (Eloquent), XML-парсинг с защитой XXE (SOAP-интеграции), ограничение размера загрузок и валидация MIME.
- **Rate limiting**: на формы аутентификации (brute-force), на API по пользователю/токену/IP.
- **Аутентификация**: LDAP/AD + SSO (SAML/OAuth 2.0), 2FA TOTP, обязательная ротация токенов, принудительный logout всех сессий.
- **Авторизация**: RBAC + ABAC; запрет по умолчанию (Policies), проверка на каждом эндпоинте и в UI (middleware + store прав).
- **Данные**: маскирование персональных данных в логах (Laravel PII-redaction), шифрование чувствительных полей (Laravel `encrypted` casts), доступ к файлам через signed URLs.
- **Аудит**: журнал действий (кто/что/когда/контекст), неизменяемость (append-only).
- **SAST/SCA**: PHPStan level 8, `composer audit`, `npm audit`, Trivy для Docker-образов, регулярный пентест перед релизом.

## 11. Тестирование и качество

### 11.1. Пирамида тестов

```
            /\
           /  \   Playwright E2E (критические пути: логин,
          /----\  новости, задачи, документы, опросы)
         /      \
        /  Feature\  PHPUnit feature (API-эндпоинты, политики,
       /  (API)    \  рабочие процессы модулей)
      /-------------\
     / Unit + Vitest \  PHPUnit unit (Actions/Services), Vitest
    /_________________\  (компоненты Vue + Pinia-сторы)
```

### 11.2. Инструменты и цели

| Слой | Инструмент | Цель |
|---|---|---|
| Backend unit/feature | PHPUnit + RefreshDatabase/factories | покрытие ≥ 70 % |
| Frontend components | Vitest + @vue/test-utils | ключевые компоненты, стори-моки |
| E2E | Playwright | критические пути в свежем окружении |
| Нагрузка | k6 | 3 000 пользователей, P95 < 500 мс |
| Перформанс/доступность | Lighthouse CI | Perf ≥ 85, A11y ≥ 90 на ключевых страницах |
| Lint/формат | PHP CS Fixer, ESLint, Prettier, Pint | единый стиль (PSR-12, Vue Style Guide) |
| Static analysis | PHPStan level 8 | типизация и поиск дефектов |

### 11.3. Нагрузочный сценарий (k6)

- Профиль: 10 % новых сессий входа, 90 % «горячие» пользователи (лента, дашборд, задачи).
- Проверяемые эндпоинты: login, `/news`, `/dashboard`, `/tasks/kanban`, `/search`, `/notifications`.
- Цели: RPS и P95 по каждому эндпоинту; регрессия кэша и очередей.
- Прогон на каждом этапе с релизами, полный прогон — этап 10.

## 12. CI/CD

### 12.1. Git-флоу

- `main` — production; `staging` — предрелиз; feature-ветки от `staging` (или от `main` при feature-driven релизах — фиксируется на этапе 0).
- Code review: обязателен, минимум 1 аппрув; защищённые ветки, статус-чеки обязательны.

### 12.2. Пайплайн

```
[commit] --> lint (Pint, ESLint, Prettier)
          --> static analysis (PHPStan 8, tsc, vue-tsc)
          --> security (composer audit, npm audit, Trivy)
          --> tests (PHPUnit, Vitest)
          --> build (docker build backend/frontend + тег)
          --> deploy staging + smoke tests (Playwright)
          --> [manual approve] --> deploy prod (rolling, zero-downtime)
          --> E2E + Lighthouse CI (prod)
```

- Каждый merge в `staging` — автоматический деплой на staging; в `main` — по тегу релиза после ручного подтверждения.
- Артефакты: Docker-образы в приватном registry, OpenAPI-спецификация как артефакт.

## 13. Мониторинг и наблюдаемость

- **Health-check**: `/health/live` (процесс), `/health/ready` (БД, Redis, S3, LDAP, очереди) — используются LB и оркестратором.
- **Метрики**: Prometheus (список метрик приложения: latency P50/P95/P99, throughput, глубина очередей, число WebSocket-соединений, ошибки).
- **Дашборды Grafana**: Laravel/PHP-FPM, PostgreSQL (репликация, блокировки), Redis, Node/Nitro, очереди.
- **Алерты**: error rate, P95 выше порога, глубина очереди, недоступность зависимостей, SSL-сроки.
- **Логи**: структурированные JSON-логи (request id, trace id), PII-редакция, ротация, агрегация (Loki/ELK — по выбору).
- **Ошибки**: Sentry (backend + frontend), source maps для прода.
- **SLO/SLA**: аптайм 99,5 %, плановые окна обслуживания в часы минимальной нагрузки.

## 14. Дорожная карта (этапы и вехи)

Оценка для команды 7–8 человек. Backend и frontend по каждому этапу идут параллельно.

| # | Этап | Длительность | Ключевой результат | Критерий выхода |
|---|---|---|---|---|
| 0 | Фундамент и инфраструктура | 2–3 нед | Репозитории, docker-compose, каркасы Laravel/Nuxt, базовые миграции, CI-скелет, health-check | `docker compose up` поднимает пустой портал; пайплайн зелёный |
| 1 | Аутентификация и авторизация | 3–4 нед | LDAP-вход, сессии, Sanctum-токены, 2FA, RBAC+ABAC, SSO-заглушка, аудит входа | Логин через AD, разграничение прав, 2FA, принудительный logout |

| 7 | Справочники + Поиск | 3–4 нед | Телефонный справочник, нормативные документы, глобальный поиск с фасетами и подсветкой | Поиск по людям/документам/новостям/задачам |
| 8 | Администрирование и аудит | 2–3 нед | Пользователи/роли/права, аудит-журнал, конфигурация портала (темы, логотип, баннеры), мониторинг очередей/сессий | Панель админа покрывает все модули |

Зависимости: этап 1 блокирует все остальные; этапы 2–8 после 1 могут идти параллельными потоками (несколько scrum-команд), этап 9 — в основном параллельно 3–7.

## 17. Критерии приёмки

Маппинг на раздел 9 требований:

- [ ] Развёртывание из одного `docker-compose.yml` командой `docker compose up` (staging-окружение).
- [ ] Все E2E-тесты (Playwright) проходят в свежем окружении (чистый checkout + `compose up`).
- [ ] Нагрузочный тест: 3 000 одновременных пользователей, P95 < 500 мс.
- [ ] Аудит безопасности без критических уязвимостей (SAST + ручной пентест).
- [ ] Lighthouse-аудит всех ключевых страниц: Performance ≥ 85, Accessibility ≥ 90, FCP ≤ 1,5 с.
- [ ] Документация: README с инструкцией запуска, OpenAPI-спецификация, схема БД (в `docs/`).
- [ ] Бэкапы: ежедневные инкрементальные, еженедельные полные, хранение 30 дней, протестировано восстановление.
- [ ] Покрытие backend-тестами ≥ 70 %.

## 18. Definition of Done

Для каждой задачи (user story / таска):

- [ ] Код написан по стандартам (PSR-12 / Vue Style Guide), прошёл линтеры.
- [ ] PHPStan level 8 без ошибок (backend).
- [ ] Написаны/обновлены unit- и feature-тесты; покрытие новых строк ≥ 80 %.
- [ ] Для новых эндпоинтов обновлена OpenAPI-спецификация и TS-типы фронтенда.
- [ ] Для новых таблиц — миграция + reverse-миграция; схема отражена в docs.
- [ ] Доступность: разметка, aria, клавиатурная навигация проверены.
- [ ] Локализация: все пользовательские строки вынесены в i18n (ru/en).
- [ ] Аудит-события и уведомления добавлены там, где применимо.
- [ ] Code review пройден (минимум 1 аппрув), замечания закрыты.
- [ ] E2E-тест критического пути (если затронут) зелёный.
- [ ] Метрики производительности не регрессировали (сравнение с базовым прогоном).

## 19. Открытые вопросы

Решения, которые необходимо зафиксировать до конца этапа 0:

1. **Монорепозиторий vs polyrepo** (требования описывают структуру единого репозитория — подтвердить).
2. **Scramble vs Scribe** для генерации OpenAPI.
3. **Нужен ли OpenSearch в MVP** или PostgreSQL FTS достаточно на год вперёд.
4. **Чат** (упомянут в требованиях §3 «уведомления и чат») — объём MVP: только уведомления или полноценный чат с историей.
5. **Подписи документов**: простая электронная подпись (PIN/TOTP) или только интеграция с внешней СЭД.
6. **SAML-IdP**: какой провайдер используется в организации (AD FS, Keycloak и т.п.).
7. **Vault vs env-переменные** для секретов.
8. **Оркестрация прода**: Kubernetes (Helm) или Ansible + systemd.
9. **Механизм импорта оргструктуры**: только XLSX/CSV или также live-синхронизация из ERP.
10. **Индексация файлов** (PDF/DOCX в поиске) — извлекать текст или искать только по метаданным.

> После фиксации решений целесообразно перевести данный документ в структуру OpenSpec (capability specs + design + tasks) для пошаговой реализации каждого этапа.
