# Дорожная карта OpenSpec: детализация этапов 0–10

| Поле | Значение |
|---|---|
| Источник | [`DEVELOPMENT_PLAN.md`](./DEVELOPMENT_PLAN.md), раздел 14 «Дорожная карта» |
| Методология | OpenSpec: каждый пункт = одно изменение (`openspec/changes/<id>/`) |
| Оценка | 7–8 человек; backend и frontend по каждому этапу идут параллельно |
| Статус | Черновик (draft) |

---

## Как читать дорожную карту

- **Один пункт = одно OpenSpec-изменение.** Внутри изменения создаются артефакты: `specs/` (delta-спецификации), `design.md` (ADR-решение), `tasks.md` (задачи с DoD из раздела 18 плана).
- **Порядок пунктов внутри этапа — последовательность выполнения.** Пометка `[P]` — можно вести параллельным потоком (backend / frontend).
- **Этап завершён**, когда все его изменения предложены → применены → заархивированы (flow: propose → apply → archive), а критерий выхода этапа подтверждён.
- **Сквозные требования** (безопасность, i18n ru/en, WCAG AA, тесты ≥ 70 %, OpenAPI + TS-типы, аудит-логи, уведомления) применяются к каждому изменению через Definition of Done — в тексте ниже не повторяются.

## Этап 0. Фундамент и инфраструктура (2–3 недели)

- **OS-0.1** Монорепо-скелет: структура `backend/`, `frontend/`, `docker/`, `docs/`, `deploy/`; git-флоу; README; шаблоны коммитов.
- **OS-0.2** Docker Compose dev-стенд: `nginx`, `php:8.4-fpm-trixie-slim`, `worker`, `scheduler`, `reverb`, `frontend` (Nitro), `postgres:18`, `redis:7`, `minio`, `mailpit`.
- **OS-0.3** Каркас Laravel 13: модульная структура `app/Modules/` + `app/Shared/`, базовые миграции `users`, `departments`, `positions`, конфиги.
- **OS-0.4** Health-check: `GET /health/live` и `GET /health/ready` (БД, Redis, S3, LDAP-заглушка, очереди).
- **OS-0.5** Каркас Nuxt 4: `pages/layouts/components/composables/stores/middleware/plugins`; Vuetify 3; `@nuxtjs/i18n` (ru/en); `routeRules` SSR/SPA per-route.
- **OS-0.6** API-клиент фронтенда: `utils/api.ts` (Auth-заголовки, retry, интерцептор 401/тостов); генерация TS-типов из OpenAPI.
- **OS-0.7** CI-скелет: lint (Pint, ESLint, Prettier), static analysis (PHPStan 8, `vue-tsc`), security (`composer audit`, `npm audit`, Trivy), тесты (PHPUnit, Vitest), сборка Docker-образов.
- **OS-0.8** Фиксация решений этапа 0 (открытые вопросы): монорепо, Scramble vs Scribe, Vault vs env, k8s vs Ansible, OpenSearch в MVP, чат в MVP.

**Критерий выхода:** `docker compose up` поднимает пустой портал; пайплайн зелёный; решения этапа 0 зафиксированы в ADR.

## Этап 1. Аутентификация и авторизация (3–4 недели)

- **OS-1.1** Модель пользователя и LDAP-синхронизация: `users`, `user_profiles`; `ldaprecord/laravel`; идемпотентная синхронизация атрибутов с reconciliation.
- **OS-1.2** Вход через LDAP с fallback на локального пользователя: `AuthController`, сессии в Redis, logout, принудительное завершение сессий.
- **OS-1.3** Sanctum API-токены: stateless-аутентификация для API/mobile, ротация и отзыв токенов.
- **OS-1.4** 2FA TOTP (`spatie/laravel-google2fa`): включение, QR-код, verify-эндпоинт, обязательная активация по политике.
- **OS-1.5** RBAC (`spatie/laravel-permission`): роли, права, middleware `auth`/`role`/`permission`, сидеры базовых ролей.
- **OS-1.6** ABAC-сервис: контекстные правила (подразделение, иерархия руководителей, статус сотрудника, чувствительность ресурса).
- **OS-1.7** SSO-заглушка: `Contracts\AuthProvider`, SAML/OAuth 2.0-адаптер в виде заглушки, переключение провайдера конфигом.
- **OS-1.8** Аудит входа: append-only журнал `audit_logs` (вход, 2FA, logout, отказ), PII-redaction.

**Критерий выхода:** логин через AD, разграничение прав, 2FA, принудительный logout всех сессий.

## Этап 2. Личный кабинет + оргструктура (3–4 недели)

- **OS-2.1** Профиль сотрудника: `GET/PATCH /me`, редактируемые поля, аватар в MinIO (signed URL).
- **OS-2.2** Дашборд с виджетами [P]: виджеты (мои задачи, новости, опросы), SPA-роут, Pinia-состояние.
- **OS-2.3** Дерево подразделений: materialized path/closure, `GET /departments/tree`, кэширование + инвалидация.
- **OS-2.4** Импорт/экспорт оргструктуры [P]: XLSX/CSV, очередь `imports`, отчёт об ошибках импорта.
- **OS-2.5** Синхронизация с LDAP по расписанию: scheduler, джоба синхронизации, конфликт-политика (LDAP — источник истины).

**Критерий выхода:** виджеты дашборда работают; импорт оргструктуры 10 000+ строк без ошибок.

## Этап 3. Новостной портал (3–4 недели)

- **OS-3.1** Модель новостей: `news`, `news_tags`, `news_media`, `news_pins`; права на публикацию по подразделениям.
- **OS-3.2** Ленты и фильтрация: корпоративная / по подразделениям / по тегам; курсор-пагинация; `filter[...]`-параметры.
- **OS-3.3** SSR-страницы новостей [P]: `routeRules { '/news/**': { ssr: true } }`, HTTP-кэш Nginx с ETag, payload-кэш Nitro.
- **OS-3.4** Редактор и медиа: rich-text, XSS-санитизация (DOMPurify + бэкенд), загрузка вложений в MinIO.
- **OS-3.5** Модерация и публикация по расписанию: статусы (черновик → на модерации → опубликовано), scheduler публикаций, уведомления авторам.
- **OS-3.6** Комментарии [P]: анти-флуд (rate limit), модерация, real-time-обновления через Reverb.

**Критерий выхода:** полный цикл «создание → модерация → публикация по расписанию → комментарии».

## Этап 4. Документооборот (4–5 недель)

- **OS-4.1** Библиотека документов: `document_categories`, `documents`, версии `document_versions`; иерархия папок и права доступа.
- **OS-4.2** Превью PDF/DOCX/PPTX [P]: конвертация в очереди, кэш превью, streaming из MinIO.
- **OS-4.3** Жизненный цикл документа: `document_workflow_states`, переходы и согласование (policy на каждом переходе).
- **OS-4.4** Подписи: адаптер `Contracts\SignatureProvider` + заглушка СЭД; подпись PIN/TOTP как временное решение.
- **OS-4.5** Индексация документов: извлечение текста, FTS-индекс, связь с поиском (этап 7).

**Критерий выхода:** ЖЦ «черновик → согласование → опубликован → архив» с версиями и превью.

## Этап 5. Задачи и поручения (3–4 недели)

- **OS-5.1** Модель задач: `tasks`, `task_statuses`, `task_assignees`, дедлайны; права по исполнителю/автору/руководителю.
- **OS-5.2** CRUD и список задач [P]: фильтры, сортировки, `task_comments`, `task_attachments` в MinIO.
- **OS-5.3** Канбан-доска [P]: колонки по статусам, drag&drop, real-time через Reverb (echo-клиент).
- **OS-5.4** Минимальный Гант: timeline по дедлайнам, пересечения, переиспользование данных канбана.
- **OS-5.5** Уведомления о дедлайнах: scheduler-джоба, подписки `notification_subscriptions`, в UI и email.

**Критерий выхода:** канбан-доска работает в реальном времени; уведомления о дедлайнах приходят вовремя.

## Этап 6. Опросы и голосования (2–3 недели)

- **OS-6.1** Конструктор опросов: типы вопросов (один/много, шкала, текст), варианты, срок действия, целевая аудитория.
- **OS-6.2** Голосование: анонимные ответы без FK на `users`, защита от повторного участия, квоты ответов.
- **OS-6.3** Live-результаты [P]: агрегации, фасадные фильтры, real-time-обновление для автора.
- **OS-6.4** Гарантии анонимности: тесты, что по данным ответов нельзя восстановить автора; экспорт результатов.

**Критерий выхода:** анонимный опрос не раскрывает автора; результаты доступны только автору и админу.

## Этап 7. Справочники + Поиск (3–4 недели)

- **OS-7.1** Телефонный справочник [P]: `directory_entries`, `phone_book`; поиск по ФИО через `pg_trgm` (GIN).
- **OS-7.2** Нормативные документы [P]: `regulations`, версии, категории, права чтения.
- **OS-7.3** Глобальный поиск: `SearchService` над PostgreSQL FTS (новости, документы, люди, задачи), фасеты, подсветка совпадений.
- **OS-7.4** Абстракция поиска: `Contracts\SearchProvider`, подготовка к замене на OpenSearch без переписывания бизнес-кода.

**Критерий выхода:** поиск по людям/документам/новостям/задачам с фасетами и подсветкой.

## Этап 8. Администрирование и аудит (2–3 недели)

- **OS-8.1** Панель пользователей и ролей [P]: CRUD, назначение ролей/прав, блокировка, сброс 2FA.
- **OS-8.2** Аудит-журнал [P]: просмотр, фильтры (кто/что/когда), экспорт, политика хранения.
- **OS-8.3** Конфигурация портала: `config_settings` (темы, логотип, баннеры), кэш с инвалидацией.
- **OS-8.4** Мониторинг сессий и очередей: список активных сессий, принудительный logout, глубина очередей.

**Критерий выхода:** панель администратора покрывает все модули; аудит полный и неизменяемый.

## Этап 9. Интеграции (3–4 недели)

- **OS-9.1** СЭД-адаптер: `Contracts\DocumentExchange` (REST/SOAP), фиктивный стенд для разработки и тестов.
- **OS-9.2** ERP-адаптер [P]: REST/OData, синхронизация справочников (подразделения, должности) по расписанию.
- **OS-9.3** SMTP-уведомления [P]: почтовые шаблоны, очередь `notifications`, перехват в dev (Mailpit).
- **OS-9.4** Push FCM/APNs [P]: подписки устройств, серверные ключи, отправка через очередь.
- **OS-9.5** Prometheus-метрики [P]: `/metrics`, метрики приложения (latency P50/P95/P99, throughput, очереди, WebSocket-соединения).

**Критерий выхода:** интеграционные тесты с фиктивными стендами зелёные; метрики доступны Grafana.

## Этап 10. Стабилизация, нагрузка, безопасность, запуск (3–4 недели)

- **OS-10.1** Нагрузочное тестирование k6 [P]: профиль «10 % новых сессий / 90 % горячие», 3 000 пользователей, P95 < 500 мс.
- **OS-10.2** Оптимизация производительности: устранение N+1, кэш, индексы по результатам нагрузочных прогонов.
- **OS-10.3** Аудит безопасности [P]: SAST/PHPStan, Trivy, ручной пентест, закрытие findings, проверка OWASP Top 10.
- **OS-10.4** Lighthouse-аудит [P]: Performance ≥ 85, Accessibility ≥ 90, FCP ≤ 1,5 с на ключевых страницах.
- **OS-10.5** Runbook и документация: deploy/rollback, восстановление из бэкапов, инциденты, схема БД, OpenAPI.
- **OS-10.6** Релиз: E2E в свежем окружении (чистый checkout + `compose up`), чек-лист критериев приёмки (раздел 17 плана), zero-downtime деплой.

**Критерий выхода:** все критерии приёмки выполнены; релиз в эксплуатацию.

## Граф зависимостей и MVP

- **OS-1.x** блокируют все остальные этапы — выполняются первыми.
- После этапа 1 этапы 2–8 могут идти **параллельными потоками** (несколько команд); внутри этапа порядок пунктов сохраняется.
- Этап 9 (интеграции) — в основном параллельно этапам 3–7; OS-7.4 зависит от OS-7.3.
- **MVP (пилот):** OS-1.1…1.8 + OS-3.1…3.3 + OS-5.1…5.3 + OS-7.1 → достижим к концу этапа 5 (~17–20 недель).

## Итоги

- **~65 изменений** суммарно (этапы 0–10), каждое — отдельный каталог в `openspec/changes/` с циклами propose → apply → archive.
- Суммарная длительность и критерии выхода этапов — как в [`DEVELOPMENT_PLAN.md`](./DEVELOPMENT_PLAN.md), разделы 14 и 17.
- Перед стартом каждого этапа открывается его первый change (propose); решения этапа 0 (OS-0.8) фиксируются до начала OS-1.x.
